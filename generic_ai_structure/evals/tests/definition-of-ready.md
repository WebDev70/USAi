# Definition of Ready

Use before implementation for feature or product-facing work. For chores, refactors, small docs edits, or research, mark non-applicable items as N/A with justification.

## Readiness checklist

- [ ] Request is understood.
- [ ] Change type is classified.
- [ ] User story or clear goal exists.
- [ ] Stakeholder value is explicit.
- [ ] Acceptance criteria are testable.
- [ ] Work is sized as a small vertical slice.
- [ ] Scope and out-of-scope are explicit.
- [ ] Affected systems or artifacts are identified.
- [ ] Test/eval approach is known.
- [ ] Security, privacy, and data implications are known.
- [ ] Dependencies, permissions, and tools are available.
- [ ] Risks and mitigations are listed.
- [ ] Documentation/prompt/data update needs are known.

## Blocking readiness failures

The task is not ready if:

- Acceptance criteria cannot be tested or observed.
- Scope is too broad to review safely.
- Required data, permissions, or environment are unavailable.
- Security-sensitive work lacks a security review plan.
- The expected output is ambiguous.
